## Scope and data protection

This is a source update, not a station-data migration. It does not delete or rewrite production media, channel assignments, commercial inventory, Kids approvals, artwork, profiles, PINs, favourites, watchlists, or playback history. The broadcast scheduling algorithms are retained.

The reference review found no demonstrably unused application files to delete. Static logos and source portraits are retained because saved programming may reference their public URLs. The service worker is loaded by URL and must not be treated as an unused module. Next.js routes, components, styles, tests, and assets remain in their required project structure. The update is distributed as one Git bundle.

## CI follow-up: buffering status

GitHub run [#73](https://github.com/300LBHACK3R/retro-tv/actions/runs/40235065061) completed with 267 browser checks passing, 17 intentional skips, and three failures of the new sound-prompt check in the WebKit desktop, iPhone, and tablet projects. All earlier quality steps passed. The failure traces showed a remaining `Buffering…` notice after unmuting, which correctly kept the channel overlay hidden.

The playback monitor treated the media `stalled` download event as proof that playback had stopped. A fully buffered video can keep advancing after that event, and the monitor relied exclusively on another `playing` event to clear its notice and pending recovery. Two new regression checks reproduced those stale-notice paths before the correction.

The monitor now distinguishes a stalled download from an empty playback buffer. It also clears stale buffering/recovery state when the existing progress sampler observes actual playback advancing with frame data available. WebKit reproduced the problem locally: after a seek it emitted `waiting`, kept advancing its media clock at `HAVE_CURRENT_DATA`, and never emitted another `playing` event. The recovery baseline resets when waiting begins, so movement from before the stall cannot cancel a genuine reconnect. Genuine stalls retain the existing bounded reconnect behavior. The sound-prompt check still requires the overlay to become available after unmuting; it now additionally checks actual playback progress and that the buffering notice is gone.

The workflow uses the Node 24 releases of `actions/checkout`, `actions/setup-node`, and `actions/upload-artifact` (`v6`). The application's test runtime remains Node 22. The runner is explicitly Ubuntu 24.04, matching run #73, so the announced `ubuntu-latest` migration does not silently change the test platform.

This follow-up must receive a fresh green GitHub run before production promotion. The failed run is retained as evidence; no check was skipped or disabled to make it pass.
